# 0017 — 추론 ON `presence_penalty` 적용 및 의역 사고 루프 탐지·자동 복구

이 결정은 [0015 — 진행 중 턴 도구 기록 잘라내기 제거, 루프·반복 차단 및 생각 창 자동 스크롤](0015-remove-active-tool-rolling-and-add-loop-guards.md)을 보완한다.

## 실제 실행 프로그램 모니터링에서 확인된 잔여 원인

실행 중인 개발 앱(`PID 3520`, 모델 `qwen3.6-35b-a3b` Q4_K_M, 32K 컨텍스트, `msg[39]`)을 모니터링한 결과, 0015 이후 진행 중 턴 기억 상실과 다중 도구 왕복 루프는 사라졌으나 **단일 `<think>` 블록 내부**에서 새로운 형태의 무한 루프가 발생했다.

1. **추론 중 의역(paraphrase) 자기검열 루프**:
   - 모델이 `<think>` 안에서 `"아, 잠깐... index.php에 PHP 코드가 전혀 없고..."`, `"근데 php -S 실행 시..."`, `"실은 index.php가 이미 순수 HTML이라..."`처럼 앞쪽 전환 추임새와 문장 마무리를 조금씩 바꾸며 같은 결론을 4~8회 이상 되풀이하다가 답변을 출력하지 못했다.
   - 0015의 `detect_repetition_loop`은 글자 단위 제자리 반복만 검사하므로 추임새나 어미를 바꾼 의역 사고 루프를 놓쳤다.
2. **추론 ON 상태의 `presence_penalty` 미설정**:
   - 로컬 추론 모델(Qwen3.5/Qwen3.6 계열)은 추론("생각하기")이 켜져 있을 때 `presence_penalty`가 0이면 긴 `<think>` 구간에서 같은 개념·문장을 반복하는 자기검열 루프에 빠지기 쉽다.

## 변경 내용 (`src-tauri/src/agent.rs`)

1. **추론 ON 시 모드별 `presence_penalty` 자동 적용 (`thinking_presence_penalty`)**:
   - `reasoning_options`가 비어 있지 않고 추론 설정이 `"off"`가 아닌 경우에만 요청 본문에 `"presence_penalty"`를 넣는다.
   - 코딩 모드(`mode == "code"`)는 문법 토큰(괄호·키워드·들여쓰기 등) 훼손을 줄이기 위해 **`0.8`**, 일반·프로젝트·기타 모드는 **`1.2`**를 적용한다.
   - 추론 미지원 모델이거나 `"off"` 상태(컨텍스트 요약 포함)에서는 넣지 않는다.
2. **`<think>` 전용 의역 사고 루프 탐지기 (`detect_thinking_loop`, `normalize_thinking_clause`)**:
   - 기존 `detect_repetition_loop`이 참이면 즉시 차단한다.
   - 600자 이상인 사고 텍스트의 끝부분 최대 4,500자에서:
     - **절(clause) 반복**: `\n . ! ? 。 → :`로 나눈 뒤 목록 번호·강조 기호(`*`, `_`, `` ` ``, `"`, `'`)와 앞쪽 한국어 전환 추임새(`"아, 잠깐"`, `"근데"`, `"하지만"`, `"실은"`, `"아니면"`, `"일단"` 등)를 제거·정규화해 16자(고유 문자 7개) 이상인 절이 **4회 이상** 나오거나, **3회 이상** 나온 서로 다른 절이 **2개 이상**이면 루프로 판정한다.
     - **5어절 슬라이딩 싱글 반복**: 단어 수 40개 이상일 때 구두점·공백을 정리한 5어절 구문(18자·고유 문자 8개 이상)이 **5회 이상** 등장하면 루프로 판정한다.
   - 보이는 최종 답변(`acc.content`)은 정상적인 다중 라운드 요약 문장 오탐을 막기 위해 기존의 엄격한 `detect_repetition_loop`만 유지한다.
   - 실제 대화 저장소(`anylm_desktop_store.json`) 전체 메시지 검증에서 반복 사고 블록은 100% 탐지하고 정상 사고 블록(11건)에서는 오탐 0건을 확인했다.
3. **`<think>` 루프 감지 시 추론 끄기 1회 자동 재시도 + 안전 중단**:
   - 스트리밍 중(256바이트마다) 또는 라운드 종료 시 `detect_thinking_loop(&acc.reasoning)`이 감지되었고 아직 본문·도구 호출이 시작되지 않았으며 모델이 `"off"`(`reasoning_effort: "none"`)를 지원하는 경우, 해당 라운드에서는 최대 1회(한 턴 최대 2회) 망가진 `<think>`를 모델 문맥(`api_messages`)에 넣지 않고 추론을 끈 상태로 즉시 재시도한다.
   - UI 생각 창과 상태 안내에도 `[생각 반복이 감지되어 추론을 끄고 바로 진행합니다]`를 표시한다.
   - 재시도 뒤에도 다시 반복되거나 `"off"`를 지원하지 않으면 즉시 생성을 멈춰 무한 재시도를 방지한다.

## 갱신 (2026-11-25, 전체 검토 수정 2차)

검토에서 탐지기를 따로 떼어 실행해 보니 정상 작업이 루프로 판정되었다. Tailwind JSX 표 초안(같은 `<td className=...>` 줄 5개), HTML 라디오 목록 초안, 초안·수정·최종으로 세 번 적은 Rust 함수, "- src/components/X.tsx 파일은 props 타입을 export 하지 않는다" 12줄 목록이 모두 걸렸다. 재시도 2회 뒤에는 긴 작업이 멈추고, "off" 선택지가 없는 모델은 첫 오탐에서 바로 멈췄다. 또 `presence_penalty`가 도구 호출 라운드(JSON 인자)·`write_file` 내용·표에도 붙어 `"` `,` `|` 괄호가 벌점을 받을 위험이 있었다.

### `presence_penalty` 새 값 (`thinking_presence_penalty`)

| 경우 | 값 | 이유 |
|---|---|---|
| 프로젝트·코딩 화면 기본 | 넣지 않음(0) | 이 화면의 라운드는 대부분 도구 JSON 인자·파일 내용·표를 만든다. 벌점이 문법 기호를 깎아 JSON·표가 깨지거나 다른 언어가 섞일 수 있다. |
| 일반 채팅, 추론 ON | `CHAT_THINKING_PRESENCE_PENALTY = 0.5` | 도구를 거의 쓰지 않아 위험이 작고, 긴 생각의 반복을 약하게 억제한다. 1.2는 한국어 답에서 어휘가 흔들릴 만큼 컸다. |
| 사고 반복이 감지된 바로 다음 한 라운드(추론 ON) | `LOOP_RETRY_PRESENCE_PENALTY = 1.0` | 반복을 깨는 데만 잠깐 쓴다. 그 라운드가 정상으로 끝나면 기본값으로 돌아간다. |
| 추론 OFF 요청(추론 끄기 재시도, 컨텍스트 요약 포함), 추론 선택지 없는 모델 | 넣지 않음 | 기존 규칙 유지 |

### 사고 반복 복구 순서 (`ThinkingLoopRecovery`)

감지 즉시 추론을 끄던 방식을 바꿨다. 추론을 끄면 코딩 품질이 떨어지고 "off"가 없는 모델은 방법이 없었기 때문이다.

1. 본문·도구 호출이 아직 없을 때 첫 감지: 추론을 켠 채 `presence_penalty` 1.0으로 그 라운드를 다시 보낸다(생각 창 표시: `[생각 반복이 감지되어 반복 억제를 높여 다시 생각합니다]`). 추론 선택지가 없는 모델은 조절할 방법이 없어 기존처럼 멈춘다(아래 보강에서 바뀜: 이 모델도 1.0 재시도를 한 번 거친다).
2. 같은 라운드에서 다시 감지: 모델이 "off"를 지원하면 추론을 끄고 다시 보낸다(`[생각 반복이 감지되어 추론을 끄고 바로 진행합니다]`). 지원하지 않으면 멈춘다.
3. 그래도 반복되면 멈춘다. 한 턴 전체 재시도는 `MAX_THINKING_LOOP_RETRIES = 4`회까지.

재시도 단계는 그 라운드가 정상으로 끝날 때까지 유지한다. 예전에는 `std::mem::take`로 한 번 쓰고 지워서, 재시도 라운드가 연결 복구나 컨텍스트 압축 단계 올리기로 다시 보내지면 추론이 다시 켜졌고, 이어서 반복이 나오면 "이미 재시도했다"로 곧바로 멈췄다.

### 탐지기 조정 (`detect_thinking_loop`, `detect_repetition_loop`)

- 코드 블록(``` … ```, 닫히지 않은 블록은 끝까지), 표 줄(`|`로 시작), 코드처럼 보이는 줄(4칸·탭 들여쓰기(아래 보강에서 바뀜: 들여쓰기만으로는 코드로 보지 않음), `<`·`{`·`}` 등으로 시작, `;`·`{`로 끝남, `=>`·`::`·`</` 포함, `fn `·`let `·`def ` 등으로 시작)을 빼고 글만 검사한다. 걷어 낸 자리에는 서로 다른 짧은 표시를 넣어 코드 앞뒤 글이 붙어 반복처럼 보이지 않게 한다.
- 절은 `.`·`:` 뒤가 공백이거나 끝일 때만 나눈다(`app.js`, `src/a.tsx`, `http://`를 쪼개지 않는다).
- 절 반복은 같은 절 횟수와 함께 **반복이 차지하는 몫**(3회 이상 나온 절의 추가 등장 글자 수 ÷ 검사한 절 글자 수)을 본다. 같은 절 6회 이상이면서 몫 25% 이상, 또는 같은 절 4회 이상(또는 3회 이상인 절 2종류 이상)이면서 몫 40% 이상일 때 루프다. 최근 4,500자와 최근 1,500자 두 창에서 본다. 0017 표본의 몫은 약 55%다.
- 5어절 싱글 기준은 최소 5회, 단어 60개마다 1회씩 올린다. 목록 항목 줄(`- `, `* `, `1. ` 등)은 같은 틀의 문장이 많아 싱글 검사에서 뺀다(절 검사에는 남는다).
- 표 줄·코드를 포함한 원문은, 정규화한 끝 2,000자 전체가 한 주기(36~450자)로 되풀이될 때만 반복으로 본다. 같은 행 20개 표(약 800자)는 정상이고, 같은 줄을 수십 번 이상 기계적으로 쏟는 퇴화는 잡는다.
- (아래 보강에서 바뀜) 예전 문서는 탐지기가 놓친 루프를 출력 길이 이어 받기 상한(15회)과 도구 라운드 상한(50회)이 막는다고 적었다. 이는 틀렸다. `max_tokens`가 기본으로 비어 있어 한 라운드는 길이에 끝이 없다. 이어 받기 15회는 반복하던 추론을 다시 넣어 이어 가게 하고, 50라운드 상한은 한 라운드 안에는 적용되지 않는다. 그래서 아래 보강에서 라운드 추론 길이 상한을 더했다.

### 갱신 (2026-11-25, 전체 검토 수정 2차 보강)

2차 검토에서 코드 블록과 들여쓴 줄 안에 숨은 루프를 놓치는 것(예전 탐지기는 잡던 것)과 남은 오탐이 확인되어 다음처럼 고쳤다.

- **들여쓰기만으로는 코드 줄이 아니다(`is_code_like_line`)**: 들여쓴 줄은 다른 코드 신호가 있을 때만 코드로 본다. 목록 기호로 시작하는 들여쓴 줄과 한글이 대부분인 줄은 `//`·`/*`·`<`로 시작할 때만 코드로 본다. `export `·`const `·`return ` 같은 낱말로 시작해도 한글이 든 줄은 코드로 보지 않는다. 그래서 4칸·탭으로 들여 쓴 하위 목록과 "export 문제: …"로 시작하는 의역 루프가 다시 잡힌다.
- **걷어 낸 코드 묶음도 센다(`code_run_loop`)**: 코드 블록과 코드 같은 줄 묶음을 공백을 줄여 해시한다. 최근 12,000자 안에서 같은 묶음(40자 이상)이 4번 나오거나 연달아 3번 나오면 루프다. 초안·수정·최종은 같은 묶음이 2번 이하라 정상이다. 묶음 앞의 글이 새 낱말(다른 파일 이름 등)을 들여오면 내용이 나아가는 중이라 세지 않는다. 그래서 파일마다 같은 diff 줄은 정상이다.
- **긴 주기의 원문 반복(`saturated_repetition`)**: 주기 36~450자 검사는 그대로 두었다. 여기에 451~2,000자 주기를 더했다. 정규화한 끝 80자가 앞에서 다시 나온 자리만 주기 후보로 삼아 싸게 찾는다. 원문 끝 max(2,000자, 주기 × 4) 전체가 그 주기로 되풀이되면 반복이다. 약 556자 TSX 블록 20번(닫히지 않은 블록 포함)이 걸린다.
- **같은 틀 산문 오탐(M1)**: 5어절 싱글은 절 안에서 위치가 같으면 다시 세지 않는다(같은 틀의 문장은 같은 자리에 같은 싱글이 온다). 글이 계속 새 낱말을 들여오는 중이면(최근 6줄 이상에서 새 낱말이 든 줄 비율 0.5 이상) 절 반복 검사도 루프로 보지 않는다. 다음 입력은 이제 정상으로 본다: 목록 기호 없는 "src/components/X.tsx 파일은 props 타입을 export 하지 않는다" 12줄, 끝 문장이 같은 파일별 판정 12개, 같은 틀로 쓴 화면 분석 10개, 같은 틀 문장 30개. 0017 표본과 목록·들여쓴 목록 의역 루프는 여전히 잡는다.
- **라운드 추론 길이 상한(`reasoning_hard_cap`)**: 한 라운드의 추론이 상한을 넘으면 탐지기가 못 잡은 루프로 본다. 상한은 컨텍스트 3개 분량의 글자 수다. 처리는 반복 억제 → 추론 끄기 → 멈춤 순서를 따른다. 보이는 답도 도구 호출도 없이 길이 제한으로 이어 받은 라운드들의 추론은 합쳐서 센다. 글자 수 어림과 모르는 컨텍스트 처리는 아래 "보강 2"에서 바뀌었다. 처음에는 토큰당 1.5자로 어림했고, 컨텍스트를 모르면 8,192로 보아 40,000자였다.
- **출력과 함께 온 반복 판정(M8)**: 라운드 끝에서 사고 반복으로 판정됐는데 그 라운드에 보이는 답이나 도구 호출이 있으면, 버리거나 멈추지 않는다. 출력은 그대로 쓰고 도구도 실행한다. 다음 라운드 한 번만 `presence_penalty` 1.0을 넣는다(`penalize_next_round`). 재시도 횟수와 따로 센다(아래 보강 2).
- **쓸모없는 재시도 단계 건너뛰기(M3)**: 사용자가 추론을 꺼 두었으면 반복 억제를 넣지 않으므로 같은 요청을 다시 보내게 된다. 이때는 그 단계를 건너뛰고, 더 끌 것도 없으면 바로 멈춘다. 추론 선택지가 없는 모델도 1.0 재시도 단계를 한 번 거친 뒤 멈춘다.
- **프로젝트 대화는 기본 `presence_penalty` 없음(M2)**: 화면 값이 비어 있는 예전 프로젝트 대화는 `mode`가 ""라서 일반 채팅의 0.5를 받았다. 이제 요청에 프로젝트가 있으면 화면 값과 상관없이 기본값을 넣지 않는다. 반복 직후 재시도의 1.0은 예외다.
- 남은 한계(검토 M4): 반복 직후 재시도 라운드의 1.0은 프로젝트·코딩 화면에서도 그 라운드 전체에 붙는다. 도구 JSON 인자와 `write_file` 내용도 벌점을 받으므로, 그 라운드의 도구 인자가 깨지지 않는지 실제 모델로 확인해야 한다(STATUS 수동 확인 목록).
- 남은 한계: 줄 번호만 바뀌는 표 행 300개처럼 낱말이 새로 나오지 않는 표·코드 반복은 짧은 주기 검사에 걸리지 않을 수 있다. 이 경우는 라운드 추론 길이 상한이 막는다. "케이스 N: 같은 문장" 15줄 같은 번호 붙은 같은 문장 나열은 여전히 루프로 본다(예전 탐지기도 그랬다).

### 갱신 (2026-11-25, 전체 검토 수정 2차 보강 2)

보강 뒤 다시 한 검토에서 다음 문제가 나왔다. 한 낱말 말머리를 돌려 쓰는 영어 의역 루프와 번호 붙은 루프를 놓쳤다. 코드 같은 줄로 도는 루프도 놓쳤다. 또 컨텍스트를 모를 때 추론 상한이 너무 낮았다. 이를 다음처럼 고쳤다.

- **영어 추임새와 번호**:
  - `THINKING_FILLERS`에 `hold on`, `wait`, `actually`, `hmm`, `but`, `so`, `okay`, `ok`, `right`, `well`, `oh`를 더했다. 절은 소문자로 바꾼 뒤 비교한다.
  - 절 앞의 번호 낱말(`7번째`, `#7`, `(7)`)과 차례 표시(`step 7`, `attempt 3`, `단계 2` 등)는 떼어 내고 비교한다.
  - 새 낱말 판단에서는 숫자가 든 낱말을 뺀다. 줄마다 바뀌는 번호는 새 내용이 아니다.
- **한 낱말 말머리 싱글**: 같은 5어절 구문이 절 안의 같은 자리에 다시 나와도, 앞 낱말이 바뀌었고 그 절이 새 낱말을 들여오지 않으면 센다. "Wait, X", "So X", "But X"가 여기에 해당한다. 틀 문장은 이름이 새로 나와서 세지 않는다.
- **창마다 새 낱말 비율**: 넓은 창(4,500자)과 좁은 창(1,500자)의 비율을 따로 본다. 앞에서 잘 나아가던 사고 끝에 막 시작된 루프도 좁은 창에서 잡힌다.
- **코드 같은 줄 루프(`code_line_loop`)**: 이어진 코드 같은 줄은 한 묶음으로 해시되므로, `=>`·`()`가 든 문장으로 도는 루프는 묶음 해시가 되풀이되지 않는다. 그래서 코드 블록·표 밖의 코드 같은 줄을 하나씩도 본다. 추임새와 번호를 떼고 24자 이상인 줄이 새 낱말 없이 8번 되풀이되면 루프다. 코드 블록·표 안은 이 검사를 하지 않는다(같은 행 20개 표 초안은 정상). 초안·수정·최종(3번)과 파일마다 같은 diff 줄(사이에 새 파일 이름)은 걸리지 않는다.
- **검사 비용**: 반복 검사는 추론 끝 20,000자만 본다(`THINKING_SCAN_CHARS`). 잘라 낸 앞부분에서 코드 블록이 열린 채 끝났으면 여는 줄을 붙인다. 스트리밍 중에는 처음 16KB까지 256바이트마다, 그 뒤로는 2KB마다 검사한다. 150,000자 추론에서 검사 한 번은 약 5.6ms다(검토 측정 10.6ms).
- **추론 길이 상한의 글자 수 어림**:
  - 상한은 max(최소, 컨텍스트 × 토큰당 글자 수 × 3)다.
  - 토큰당 글자 수는 공백이 아닌 글자 가운데 ASCII 비율로 1.5자(한국어 등)와 4자(영어) 사이를 잇는다. 그래서 영어 추론도 "컨텍스트 3개 분량"이 실제로 3개 분량이다.
  - 공급자가 로드된 컨텍스트를 알려 주면 최소 40,000자다.
  - 모르면 32,768로 보고 최소 120,000자다. LM Studio JIT 로드처럼 로드 목록에 없을 때, 최대 컨텍스트를 알리지 않는 OpenAI 호환 서버일 때가 여기에 해당한다(`TurnRequest.loaded_context`).
  - 예전에는 모르는 컨텍스트를 8,192로 보아 40,000자에서 끊었고, 32K~128K 서버의 정상적인 긴 영어 추론을 잘랐다.
- **답이 나온 뒤의 추론**:
  - 답이 나온 뒤에도 추론이 이어지면 반복 검사와 길이 상한 검사를 계속한다. 도구 호출 인자가 오는 중에만 쉰다.
  - 걸리면 스트림을 끊는다. 나온 답은 살리고, 길이 제한처럼 이어 받는다. 이때 반복하던 추론은 다시 넣지 않고, 다음 라운드에 반복 억제를 올린다.
- **출력과 함께 온 반복 판정의 반복 억제는 따로 센다**: 한 턴에 4번까지 센다(`MAX_OUTPUT_LOOP_PENALTIES`). 재시도 횟수(`MAX_THINKING_LOOP_RETRIES`)와 재시도 단계는 쓰지 않는다. 그래서 그 뒤에 나온 답 없는 반복도 반복 억제 재시도부터 밟는다.
- 남은 한계: 같은 계획 문장과 같은 확인 문장을 "단계 0~3"처럼 번호만 바꿔 4번 되풀이하는 사고(검토의 "plan restated 4x", 경계 사례)는 이제 루프로 본다. 예전에는 줄마다 번호가 든 낱말을 새 낱말로 세어 정상으로 보았다. 걸려도 멈추지 않고 반복 억제를 올려 그 라운드를 다시 보낸다.
